Hướng dẫn triển khai eUni (3 repo độc lập)

Đưa euni-api-dotnet (cms-api .NET + PostgreSQL), euni-admin (CMS) và euni-public (website + cổng My eUni) lên máy chủ khi mỗi phần nằm ở một repo riêng. Làm lần lượt; mỗi bước có lệnh kiểm tra.

3 repo · 3 tiến trình · 1 databaseĐăng nhập Microsoft Entra IDRow-Level Security theo tenantFE không phải sửa mã khi đổi API

2 Tách thành 3 repo

Hiện cả ba thư mục nằm trong repo eUni_dev. Có hai cách tách; chọn một. Nên giữ lịch sử commit (cách A).

Cách A — giữ lịch sử (khuyến nghị)

Tạo 3 repo trống trên GitHub (hoặc GitLab), rồi chạy trong bản clone của eUni_dev:

bash
git clone <eUni_dev> split && cd split
for d in euni-api-dotnet euni-admin euni-public; do
  git subtree split --prefix=$d -b split/$d              # nhánh chỉ chứa lịch sử của thư mục đó, gốc là thư mục
  git push git@github.com:<org>/$d.git split/$d:main    # đẩy lên repo mới (nhánh main)
done

Hoặc dùng git filter-repo --subdirectory-filter <thư-mục> trên 3 bản clone riêng nếu muốn lịch sử gọn hơn.

Giữ ba repo tương thích với nhau

  • Hợp đồng nằm ở repo API (contract/API_CONTRACT.md + openapi.json). Đổi hợp đồng = PR ở repo API, kèm cập nhật smoke.mjs (bộ 118 kiểm tra); sau đó mới sửa FE.
  • Thay đổi tương thích ngược (thêm trường, thêm endpoint): triển khai API trước, FE sau. Thay đổi phá vỡ (đổi tên trường, đổi mã trạng thái): thêm endpoint/trường mới, giữ cái cũ cho tới khi cả hai FE đã lên bản mới, rồi mới gỡ.
  • Gắn tag phát hành ở mỗi repo (v1.4.0) và ghi trong README FE: "chạy với API ≥ vX". Rollback từng repo độc lập; lược đồ database chỉ thêm, không xóa cột nên API bản cũ vẫn chạy trên database đã nâng.

Thứ tự triển khai lần đầu: PostgreSQL → API → kiểm tra API → euni-public → euni-admin → Entra (Redirect URI) → kiểm tra cuối.

kiểm tra RLS bằng role ứng dụng

9 Proxy và tên miền

nginx
# API
server {
    server_name api.humg.edu.vn;
    listen 443 ssl;
    location /euni-api/ {
        proxy_pass http://127.0.0.1:3000;        # giữ tiền tố: API nhận cả có và không có BASE_PATH
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        client_max_body_size 50m;
    }
}
# CMS
server { server_name cms.humg.edu.vn; listen 443 ssl; location / { proxy_pass http://127.0.0.1:3001; proxy_set_header Host $host; proxy_set_header X-Forwarded-Host $host; proxy_set_header X-Forwarded-Proto $scheme; } }
# Website: trường + mọi tên miền Khoa/Phòng đều về euni-public, GIỮ NGUYÊN Host
server { server_name www.humg.edu.vn cntt.humg.edu.vn; listen 443 ssl; location / { proxy_pass http://127.0.0.1:3002; proxy_set_header Host $host; proxy_set_header X-Forwarded-Host $host; proxy_set_header X-Forwarded-Proto $scheme; } }
  • Website phân biệt trang (tenant) theo tên miền → proxy phải chuyển nguyên Host/X-Forwarded-Host. Thêm Khoa mới: DNS + chứng chỉ + thêm tên miền vào server_name (hoặc dùng chứng chỉ wildcard) — không cần build lại FE.
  • Chặn /api/v1/dev/ (đặt lại dữ liệu) ở proxy API.
  • Nếu đặt API dưới gateway có sẵn (APISIX): thêm route cms-api, auth-api (mock, tắt khi dùng Entra) trỏ về 127.0.0.1:3000; APISIX chỉ làm gateway/TLS — API tự kiểm tra token và quyền, không đổi cấu hình SSO.

10 Đăng nhập Microsoft Entra ID

Mỗi website tự đăng nhập OIDC + PKCE trực tiếp với Entra (không qua API), rồi gửi id_token làm Bearer tới API. API kiểm tra chữ ký (khóa lấy từ https://login.microsoftonline.com/<tenant>/v2.0/.well-known/openid-configuration), issuer, audience (= client id), hạn dùng.

  1. Redirect URI của app (Azure → App registrations → Authentication, loại Single-page application): thêm {origin}/dang-nhap/sso/callback cho từng origin đang dùng: https://cms.humg.edu.vn, https://www.humg.edu.vn và mỗi tên miền Khoa/Phòng có đăng nhập (Entra không cho ký tự đại diện). Đăng xuất: {origin}/dang-nhap.
  2. App roles (Azure → App roles): tạo role với giá trị cms.admin, cms.editor, cms.reviewer, cms.author, cms.viewer (và nếu muốn: student, lecturer, staff, manager, parent). Gán cho người dùng/nhóm ở Enterprise applications → Users and groups. Role xuất hiện trong claim roles của id_token.
    Bắt buộc với CMSeuni-admin quyết định cho vào /cms dựa trên claim roles trong token (role bắt đầu bằng cms.). Người chưa được gán App role sẽ không vào được CMS dù API cho phép. CMS_BOOTSTRAP_ADMINS chỉ cấp quyền ở phía API; vẫn cần gán App role cms.admin cho tài khoản quản trị đầu tiên.
  3. Claim email: Token configuration → thêm optional claim email cho id_token (API ghép người dùng với danh bạ theo email/UPN). Dùng nhóm thay App role: thêm claim groups và đặt OIDC_GROUP_ROLES ở API (FE không đọc nhóm Entra dạng GUID nên vẫn cần App role cho việc vào CMS).
  4. Cấu hình FE (mục 8) và API (mục 7) dùng cùng tenant id c852d62b-3032-4cdc-96ab-30e4368fabd7 và client id 5a7cce06-4b5c-4612-b1fa-0ef7f0702a27.
  5. Phân quyền theo trang không cấu hình trên Entra: cms.admin toàn quyền mọi trang; các vai trò khác cần grant (CMS → Phân quyền: theo trang, chuyên mục, đơn vị, bản ghi).

Người dùng được xác định thế nào ở API

  • Định danh = oid của Entra (ổn định theo tenant), không dùng sub (khác nhau theo từng ứng dụng).
  • Nếu email/UPN khớp một người trong cms.user_directory: dùng sub, đơn vị, tenant, mã cán bộ/sinh viên của danh bạ; role = hợp của role trong token và danh bạ. Người bị khóa trong danh bạ → 401.
  • Người chưa có trong danh bạ: dùng được với role từ token (thường chỉ cổng cá nhân); quản trị CMS cần role CMS và grant.

11 File media (MinIO / S3)

  1. Tạo user MinIO có quyền đọc/ghi/xóa trên bucket cms-public (API tự tạo bucket nếu chưa có và user được phép).
  2. API: STORAGE_PROVIDER=s3, S3_ENDPOINT, S3_ACCESS_KEY, S3_SECRET_KEY, S3_BUCKET=cms-public, S3_FORCE_PATH_STYLE=true (MinIO).
  3. Không mở bucket ra Internet: API phục vụ file qua URL tương đối cũ cms-api/uploads/<object_key>, ảnh trên website không đổi đường dẫn.

Nếu ghi database lỗi sau khi đã tải file lên, API tự xóa file vừa tải (bù trừ); nếu xóa cũng lỗi, lỗi được ghi ra stderr và trả về. Chuyển file đang lưu đĩa sang MinIO: sao chép nội dung uploads/ vào bucket theo đúng object_key trong cms.media. Bucket cms-private (đính kèm thông báo) chưa làm.

15 Xử lý lỗi thường gặp

Đăng nhập Entra: AADSTS50011 (redirect URI không khớp)

Origin hiện tại chưa có trong Redirect URI của app (loại SPA). Thêm đúng https://<origin>/dang-nhap/sso/callback (khớp chính xác scheme, host, cổng). Mỗi tên miền Khoa phải được thêm riêng.

Đăng nhập thành công nhưng vào CMS bị từ chối ("không có quyền")

Id_token không có claim roles chứa cms.*: gán App role cho người dùng ở Enterprise applications và đăng nhập lại (token cũ vẫn mang quyền cũ). Kiểm tra token tại jwt.ms (chỉ dùng với tài khoản thử).

API trả 401 với token Entra hợp lệ

Kiểm tra: ENTRA_TENANT_ID/ENTRA_CLIENT_ID khớp FE; token là id_token v2.0 (ver: 2.0); đồng hồ máy chủ đúng (sai quá 1 phút → hết hạn/chưa hiệu lực); người dùng không bị khóa trong cms.user_directory (status = 1); máy chủ API ra được login.microsoftonline.com (tải khóa ký) — mở tường lửa/proxy nếu cần.

Người dùng Entra vào được CMS nhưng không thấy trang/bài nào

Chỉ cms.admin được toàn quyền. Vai trò khác cần grant tại CMS → Phân quyền, và email phải khớp danh bạ để ghép đúng người (hoặc cấp grant theo role role:cms.editor).

API thoát ngay lúc khởi động: permission denied / must be owner

DATABASE_ADMIN_URL phải là role sở hữu database/schema cms (cms_admin).

Không tạo được extension ltree/unaccent/pg_trgm

Cài gói contrib (Debian/Ubuntu: postgresql-16 đã gồm). Nếu vẫn lỗi, superuser chạy CREATE EXTENSION unaccent, pg_trgm, ltree trong database.

Request đọc đều rỗng, hoặc 400 "Tenant … không tồn tại hoặc đã tắt"

DATABASE_URL sai role, hoặc tenant gửi lên (X-Tenant/tên miền) không có trong cms.tenants hoặc đã tắt: select id, is_active from cms.tenants.

Trình duyệt báo CORS

Origin chưa nằm trong CORS_ORIGINS (khớp chính xác scheme + host + cổng). Header X-Tenant, If-Match đã được cho phép.

Ảnh vỡ sau khi đặt sau gateway

URL media là đường dẫn tương đối cms-api/uploads/… được FE ghép vào NEXT_PUBLIC_API_GATEWAY_URL: biến đó phải gồm tiền tố gateway, và proxy phải chuyển /cms-api/uploads/ về API.

Sau khi đổi NEXT_PUBLIC_* website vẫn dùng giá trị cũ

Biến được nhúng lúc build: chạy lại npm run build rồi restart.

409 "Dữ liệu bị trùng …" / 422 "Dữ liệu không hợp lệ …"

Vi phạm ràng buộc database (trùng slug/mã, tham chiếu không tồn tại, giá trị ngoài danh sách); tên ràng buộc nằm trong thông báo. Không phải lỗi hệ thống.

Muốn khởi động với database trống, không nạp dữ liệu mẫu

Hiện chưa có công tắc. Cách làm: áp lược đồ bằng psql, tự tạo dòng cms.app_meta(key='schemaVersion', value='6') để API coi như đã khởi tạo, rồi đồng bộ tenant, đơn vị, danh bạ vào cms.tenants, cms.org_units, cms.user_directory.

Sự kiện outbox kẹt (attempts = 8, processed_at rỗng)

Đọc last_error, khắc phục nguyên nhân, rồi update cms.outbox set attempts = 0, available_at = now() where id = ….
